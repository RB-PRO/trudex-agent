# Методология обогащения лидов по ИНН

Инструкция для агента. Агент получает папку со списком ИНН и возвращает JSON строго по схеме `leads_schema.json`.

## Обмен файлами

- Вход: файл со списком ИНН в рабочей папке (по умолчанию `inn_list.txt`, один ИНН на строку, UTF-8). Один проход — до ~100 ИНН.
- Выход: `leads_result.json` в той же папке. Массив объектов, одна запись = один ИНН из входного списка. Кодировка UTF-8.
- Формат записи — строго по `leads_schema.json`. Ничего не выдумывать: не найдено → `null` или пустая строка.

## Пайплайн (порядок обязателен)

### Шаг 1. Эталон по каждому ИНН — egrul.nalog.ru

Неофициальный JSON-API ФНС (не требует ключа):
1. `POST https://egrul.nalog.ru/` (с заголовками браузера) с телом `vyp3CaptchaToken=&page=&query=<ИНН>&region=&PreventChromeAutocomplete=` → в ответе `t`.
2. Пауза 1–2 секунды.
3. `GET https://egrul.nalog.ru/search-result/<t>` → JSON: название (`c`), директор (`g`), дата регистрации (`r`), регион (`k`), статус (`e` — пусто = действующее, «В процессе банкротства», «Ликвидировано» и т.п.).

Это эталон. Всё, что найдено дальше, сверяется с ним по ИНН или точному названию. Не сошлось — не берём.

### Шаг 2. Агрегаторы через веб-поиск — ЕДИНЫЙ ПРОМТ

Один ИНН = один запрос, строго в формате:

```
"<ИНН>" <Название из эталона>
```

Длинные промты («ИНН выручка сайт телефон 2025») дают мусор — не использовать. Короткий промт с ИНН в кавычках достаёт карточки компаний на агрегаторах.

Источники (в порядке ценности): rusprofile.ru, checko.ru, saby.ru, audit-it.ru, zachestnyibiznes.ru, companies.rbc.ru, list-org.com, spark-interfax.ru, b2b.house.

Из карточек забираем: выручка по годам, численность, учредители, телефон, email, суды/ИП (косвенные сигналы), ОКВЭД/деятельность.

**Второй проход — добор полей (обязателен, он даёт основную плотность данных).** Для каждой компании, где не закрыты поля, — до двух коротких запросов:

```
"<ИНН>" численность
"<ИНН>" телефон сайт
```

Численность чаще всего светится в сниппетах list-org, audit-it, РБК; телефоны — в карточках ЗЧБ, checko, реестрах СРО (npmosk.ru и др.), реестрах ЖКХ (МинЖКХ, domdata). Контакты бюджетников — на сайтах учредителей (mo.mosreg.ru, balashiha.ru, mos.ru, ranepa.ru) и trudvsem.ru (email там подтверждён через Госуслуги — это надёжный источник).

### Шаг 3. Точная выручка — РФСД ФНС (если доступна среда с загрузкой файлов)

Полный датасет бухотчётности ГИРБО: `https://tochno.st/datasets/rfsd`, архивы по годам (~260 МБ/год). Внутри CSV: колонка `inn`, выручка — `line_2110` в **тысячах рублей** (делиметр `;`). Отфильтровать по ИНН, взять 2021–2025. Приоритет выше агрегаторов. Годы 2026–2029 → всегда `null`.

Если среда не позволяет скачать ~1,3 ГБ — выручку брать из агрегаторов (точность ниже, допустимо).

### Шаг 4. Стадия банкротства — Федресурс / КАД Арбитр

- Карточка должника: `bankrot.fedresurs.ru`, дела: `kad.arbitr.ru` (поиск по ИНН).
- Правило: **«иск о банкротстве подан» ≠ стадия**. Стадия начинается с введения процедуры (наблюдение, внешнее управление, конкурсное производство, реструктуризация).
- Маппинг строго в 3 значения схемы:
  - процедура введена → `В стадии банкротства`
  - ликвидация/реорганизация-присоединение/решение о ликвидации → `В стадии ликвидации`
  - всё остальное, включая «иск подан» и «предстоящее исключение из ЕГРЮЛ» → `Действующее`
- Если источники противоречат друг другу — берём запись ЕГРЮЛ (шаг 1).

### Шаг 5. Сайт

Приоритет: официальный сайт компании. Порядок:

1. Кандидат ищется по ИНН + названию (в карточках агрегаторов поле «Сайт», в сниппетах выдачи, в email-доменах контактов).
2. **Верификация обязательна**: ИНН должен встречаться на странице сайта (обычно «Контакты»/«Реквизиты»). Без подтверждения ИНН сайт не берём — не угадываем.
3. Первый проход — `scripts/site_verify.py` (перебирает /contacts/, /requisites/ и т.п., сверяет ИНН). Крупные сайты с защитой от ботов (403/JS) он может не пройти — тогда верификация через агента (FetchURL) или через цитату реквизитов сайта в поисковой выдаче; способ помечается в `note`.
4. Не берём: домены-парковки, чужие однофимильцы, сайты без ИНН и без однозначного совпадения (название + адрес + email-домен).
5. Писать домен без `http(s)://`. Несколько доменов — через `; `.

## Как не получить бан (проверено на 50 ИНН, 12.11.2026)

Банят не за «много ИНН», а за много **прямых запросов к одному агрегатору с одного IP**. Деградация выглядит так: первые карточки открываются, потом начинаются 429/500 и хвост списка остаётся без данных. Правила, которые это снимают:

1. **Веб-поиск — основной инструмент, прямые заходы — точечно.** Один поисковый запрос `"<ИНН>"` возвращает сниппеты 5–8 агрегаторов сразу: название, директор, дата, ССЧ, телефоны — часто всё нужное без единого прямого обращения. Прямой FetchURL/urllib к агрегатору — только если сниппета не хватило.
2. **Лимиты прямых обращений:** к одному домену — не чаще 1 раза в 30–60 с; одному агрегатору — не более 10–15 обращений за проход. При первом 429 — пауза минимум 30 минут, не дожимать повторами (дожим удлиняет бан).
3. **Чередовать источники.** checko после серии запросов ловит 429 на часы; rusprofile, saby, zcb, list-org, b2b.house, companium, РБК переносят десятки обращений без жалоб. HTML кэшировать на диск (checko_fetch.py это умеет) и не перезапрашивать.
4. **egrul.nalog.ru капризен двояко:** пустые `{"rows": []}` — результат ещё не готов (повторить GET с тем же токеном, egrul_fetch.py делает сам); HTTP 500 — сервис лежит (пауза 30+ мин, дальше по кругу). Фолбэк эталона на период 500 — агрегаторы с пометкой источника в `sources` (как в проходе 12.11.2026).
5. **Списки >30 ИНН — волны по 10** с паузами между волнами; внутри волны сначала весь веб-поиск, потом (при необходимости) прямые дозаказы.
6. Сайты компаний банить не боятся — их можно проверять подряд, но с задержкой 3–5 с и не более 3–4 страниц на домен.

Итог качества: единый промт + второй проход добора + правила выше дают по 50 ИНН: название/директор 100%, выручка 82%, телефоны 54%, email 46%, сайты 24% (только верифицированные), ССЧ 46%.

## Правила обработки данных

- Директор: ФИО из эталона, разбить на фамилию/имя/отчество. Не разбивается → пустые строки, не угадывать.
- Телефон: формат `+7XXXXXXXXXX`, несколько через `; `. Email: как есть, через `; `.
- Выручка: целое, в **тысячах рублей** (как в ГИРБО). Из агрегаторов — округление до целых тысяч.
- Дата регистрации: `ДД.ММ.ГГГГ`.
- Учредители: ФИО строкой через `; `.
- Конфликт значений между источниками → берём более официальный (ЕГРЮЛ/ГИРБО > агрегаторы), не усредняем.

## Скрипты (папка `scripts/`)

Готовые утилиты для шагов 1, 3, 5 и сборки результата: `egrul_fetch.py` (эталон; повторяет GET при пустых `rows` и ждёт между ИНН), `rfsd_download.sh` + `rfsd_extract.py` (выручка РФСД), `site_verify.py` (верификация сайтов по ИНН, шаг 5), `build_result.py` + `validate_leads.py` (сборка и проверка `leads_result.json`). Обогащение с агрегаторов остаётся ручным: находки по каждому ИНН складывать в `enrich.json` (схема полей и примеры вызова — в `scripts/README.md`), затем запускать сборку.

## Надёжность

- Промежуточный результат сохранять в JSON после каждых ~10 ИНН (защита от обрыва сессии).
- Таймаут поиска → повторить запрос до 2 раз.
- ИНН, по которым эталон не нашёл компанию → запись с `name: ""` и всеми `null` (чтобы надстройка видела, что ИНН обработан).
